结合现代前端开发最佳实践，以下是关于“提示框 (Notification Banner)”的核心设计与开发要点。

## 1. 概述 (Overview)
提示框（Notification Banner）用于向用户传达重要信息、系统状态或操作反馈。它通常出现在页面的顶部、特定内容区块的上方，或者是全局持续性提示。设计时需确保信息层级清晰、不干扰核心任务，并满足无障碍（Accessibility）标准。

## 2. 状态类型与颜色规范 (Types & Colors)
提示框应根据传达信息的紧急程度和性质分为四种基础状态。颜色不仅要在视觉上区分，还必须满足 WCAG 2.1 AA 级对比度要求（文本与背景对比度至少为 4.5:1）。

| 状态类型 | 语义 | 颜色基调 (参考值) | 背景色 (轻量化) | 边框/图标/标题强调色 |
| :--- | :--- | :--- | :--- | :--- |
| **Information (信息)** | 中性通知、一般系统更新提示 | 蓝色 (Blue) | 浅蓝色 (如 `#E6F2FF`) | 深蓝色 (如 `#005A9E`) |
| **Success (成功)** | 操作成功完成、任务达成反馈 | 绿色 (Green) | 浅绿色 (如 `#EAF6ED`) | 深绿色 (如 `#137333`) |
| **Warning (警告)** | 需要注意的情况、潜在业务风险 | 黄/橙 (Yellow/Orange) | 浅黄色 (如 `#FEF7E0`) | 橙棕色 (如 `#B06000`) |
| **Error (错误)** | 操作失败、验证报错、严重故障 | 红色 (Red) | 浅红色 (如 `#FCE8E6`) | 深红色 (如 `#C5221F`) |

*注：实际色值应与产品的 Design Tokens 严格对齐，避免使用刺眼的高饱和度背景。主流做法是“浅色大背景 + 左侧深色强调边框 + 深色文字/图标”。*

## 3. 图标选择原则 (Iconography)
图标是打破语言障碍、快速传递状态色彩的关键元素。图标选择应遵循通用性和高辨识度原则。

* **图标位置**：始终放置在提示框内容的最左侧，与标题或第一行文字垂直对齐。
* **推荐图标 (基于 Material Symbols 或类似标准通用库)**：
    * **Info (信息)**：`info` (圆圈内一个 'i') 或 `info_outline`
    * **Success (成功)**：`check_circle` (圆圈内一个对号)
    * **Warning (警告)**：`warning` (实心三角形内一个感叹号)
    * **Error (错误)**：`error` (圆圈内一个感叹号) 或 `cancel` (叉号)
* **辅助图标**：如果该提示框允许用户主动隐藏，必须在最右侧提供一个清晰的 `close` (叉号) 图标按钮。

## 4. 组件解构与排版布局 (Structure & Layout)
一个具有良好拓展性和阅读体验的提示框应包含以下结构：

1.  **外层容器 (Container)**：建议具备 1px 细边框，或者在**左侧加入加粗边框**（宽度通常为 4px - 6px 的状态对应色），以增强视觉提示。内部留白需充足（如 `padding: 16px`）。
2.  **状态图标 (Status Icon)**：如上所述，尺寸建议为 20px - 24px，颜色与状态色对应。
3.  **标题 (Title - 可选)**：使用粗体 (Font-weight: 600/700)，字号可以略大于正文（如 16px 或 1.125rem）。如果是短小信息，标题可省略。
4.  **正文/描述 (Description)**：标准字号（如 14px 或 1rem），行高建议在 `1.5` 到 `1.7` 之间。文本颜色使用高对比度的深灰色或黑色，而非纯黑。
5.  **操作区 (Action Area - 可选)**：包含相关的操作动作（如“刷新页面”、“前往设置”）。此处应优先使用**文字链接**或**次级/幽灵按钮 (Secondary/Ghost Button)**，绝对避免使用显眼的主按钮 (Primary Button) 从而与页面核心操作冲突。
6.  **关闭按钮 (Close Button - 可选)**：位于右上角。对于涉及全局严重错误或必读的系统协议更新，通常不提供关闭按钮。

## 5. 交互与无障碍设计要点 (Accessibility / A11y)
参照公共数字服务标准，无障碍支持是必备项：

* **ARIA 角色定义 (Roles)**：
    * **错误/警告**：这类紧急信息，容器需添加 `role="alert"`。屏幕阅读器会打断当前朗读并立即播报此信息。
    * **成功/信息**：这类非紧急反馈，容器需添加 `role="status"`。屏幕阅读器会在当前内容播报完毕后平滑播报。
* **动态更新 (Live Regions)**：如果是通过 JS 动态插入 DOM 的提示，需要确保具备 `aria-live` 属性。
* **图标语义隐藏**：状态图标仅作为视觉辅助，必须通过 `aria-hidden="true"` 对屏幕阅读器隐藏，真实的语义通过 role 或者 visually-hidden 的盲文文本传达。
* **焦点管理 (Focus)**：表单提交报错后产生的全局 Notification，应该通过 JavaScript 将焦点自动移入该容器或其标题，确保仅使用键盘的用户知道发生了错误。
* **键盘可访问性**：关闭按钮和操作链接必须可以被 `Tab` 键聚焦，并可通过 `Enter` 或 `Space` 键激活。关闭按钮应包含 `aria-label="关闭提示"`。

## 6. 响应式适配 (Responsive Design)
* **桌面端 (Desktop)**：通常采用横向流动布局（左图标 -> 中文本 -> 右侧操作与关闭按钮）。最大宽度可作限制，避免屏幕过宽导致文本行太长难以阅读。
* **移动端 (Mobile)**：由于空间受限，建议转为**纵向堆叠布局**。尤其是“操作区（按钮/链接）”，应移动到文本内容的下方并独占一行，以确保手指点击热区（Touch Target）足够大（至少 44x44px 规范）。

## 7. 使用误区避坑 (Anti-patterns)
* **避免滥用红色 (Error)**：不要将 Error 颜色用于中性的系统通知，会导致用户产生不必要的焦虑。
* **避免内容过载**：提示框不是说明文档。文案应保持在两到三行以内。如果需要详细解释，请提供一个“了解更多”的跳转链接。
* **不要与 Toast 组件混淆**：Notification Banner 是**静态/持久化**的，通常需要用户处理或主动关闭。千万不要像轻提示 (Toast/Snackbar) 那样设置几秒钟后自动消失，这会导致阅读速度慢或使用辅助设备的用户错过关键信息。
